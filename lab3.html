Part A: SQLite Orientation & Your First Table

In Week 2, your application held state in server RAM, which vanished whenever the process restarted. Today, we transition to non-volatile relational storage using SQLite.

SQLite requires no background server process; the entire database lives inside a single file on disk.

A1. Launch the SQLite CLI

You can complete this lab either locally on your workstation (Windows/macOS) or via SSH on your personal virtual server.

In your terminal, create a project folder and open a new database file named bookshop.db:

mkdir -p ~/db-lab3
cd ~/db-lab3
sqlite3 bookshop.db

Your prompt will change to sqlite>. Enable column headers and clean tabular alignment:

.headers on
.mode box

Essential SQLite Dot-Commands: - .tables — Lists all tables in the current database. - .schema <table_name> — Displays the exact CREATE TABLE statement used to construct a table. - .quit (or Ctrl + D) — Exits the SQLite shell back to your terminal.

A2. Create the books table (Trivial)

Run your first DDL statement to construct a single table:

CREATE TABLE books (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    author TEXT NOT NULL,
    year INTEGER NOT NULL,
    price REAL NOT NULL
);

Verify that the table schema was registered:

.schema books

Insert 5 initial records using explicit column syntax:

INSERT INTO books (title, author, year, price) VALUES
('1984', 'George Orwell', 1949, 8.99),
('Animal Farm', 'George Orwell', 1945, 7.99),
('To the Lighthouse', 'Virginia Woolf', 1927, 9.99),
('Mrs Dalloway', 'Virginia Woolf', 1925, 10.50),
('Brave New World', 'Aldous Huxley', 1932, 8.50);

Verify your data:

SELECT * FROM books;

Write a filtered query using a WHERE clause to display only books published after 1930:

SELECT title, author, year FROM books WHERE year > 1930;

Checkpoint (Trivial Tier): You have verified that .schema books matches your definition, and your filtered query returns a strict subset of your data.

Part B: Relational Modeling & Schema Normalization

In flat databases or spreadsheets, storing authors directly inside a books table causes update and deletion anomalies: if Aldous Huxley dies or changes his name, you must update multiple rows; if you delete his only book, his record vanishes entirely.

We now normalize this structure into a three-table design: authors, books, and genres.

+---------+         +------------------+         +------------+
| authors | 1 --- * |      books       | * --- * |   genres   |
+---------+         +------------------+         +------------+
                             |                         |
                             +----* [book_genres] *----+

B1. Enable Foreign Key Constraints

By default, SQLite does not enforce foreign keys for backward compatibility. You must enable them on every new database connection:

PRAGMA foreign_keys = ON;

B2. Construct the Normalized Schema

Reset your workspace by dropping the initial books table:

DROP TABLE books;

Now create the normalized relational entities with explicit referential integrity constraints:

-- 1. Authors Entity
CREATE TABLE authors (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,
    nationality TEXT DEFAULT 'Unknown',
    birth_year INTEGER
);

-- 2. Books Entity (Child of authors)
CREATE TABLE books (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    author_id INTEGER NOT NULL,
    year INTEGER NOT NULL,
    price REAL NOT NULL,
    FOREIGN KEY (author_id) REFERENCES authors(id) ON DELETE RESTRICT
);

-- 3. Genres Entity
CREATE TABLE genres (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL UNIQUE,
    description TEXT
);

-- 4. Junction Table for Many-to-Many relationship (M:N)
CREATE TABLE book_genres (
    book_id INTEGER NOT NULL,
    genre_id INTEGER NOT NULL,
    PRIMARY KEY (book_id, genre_id),
    FOREIGN KEY (book_id) REFERENCES books(id) ON DELETE CASCADE,
    FOREIGN KEY (genre_id) REFERENCES genres(id) ON DELETE CASCADE
);

Why composite keys in junction tables? Defining PRIMARY KEY (book_id, genre_id) guarantees that the same genre cannot be assigned to the same book twice.

Notice the ON DELETE policies: - authors → books uses ON DELETE RESTRICT to prevent deleting an author while their books are still registered. - book_genres uses ON DELETE CASCADE so deleting a book automatically purges its genre tags.

Part C: Querying Relational Data

C1. Aggregates and Sorting

Aggregate functions summarize data across multiple rows.

Run summary statistics over your inventory:

SELECT 
    COUNT(*) AS total_books,
    AVG(price) AS average_price,
    MIN(year) AS oldest_publication,
    MAX(price) AS most_expensive
FROM books;

Use ORDER BY, LIMIT, and OFFSET to sort and paginate results:

-- Retrieve the 2 cheapest books published after 1925
SELECT title, price, year 
FROM books 
WHERE year > 1925 
ORDER BY price ASC 
LIMIT 2;

C2. Grouping: WHERE vs HAVING

  • WHERE filters individual rows before groups are formed.
  • HAVING filters aggregated groups after calculation.

Calculate the number of books written by each author, showing only authors with 2 or more books:

SELECT 
    author_id,
    COUNT(*) AS book_count,
    AVG(price) AS avg_price
FROM books
GROUP BY author_id
HAVING COUNT(*) >= 2;

C3. Relational Joins

1. INNER JOIN (Intersection)

An INNER JOIN returns only records that have matching keys in both tables:

SELECT 
    authors.name AS author_name,
    books.title,
    books.price
FROM authors
INNER JOIN books ON authors.id = books.author_id;

Notice: Gabriel García Márquez is excluded because he has no books in the database.

2. LEFT JOIN (Preserve Left Table)

A LEFT JOIN preserves all rows from the left table (authors), populating right-table columns with NULL where no match exists:

SELECT 
    authors.name AS author_name,
    books.title,
    books.price
FROM authors
LEFT JOIN books ON authors.id = books.author_id;

Notice: Gabriel García Márquez now appears in the output with NULL for title and price.

Find Records with Missing Relations

You can isolate parent entities that lack child references by checking for NULL:

SELECT authors.name 
FROM authors
LEFT JOIN books ON authors.id = books.author_id
WHERE books.id IS NULL;

Part D: Guided Lab Activities

Activity 1: Three-Table Bridge Join (Intermediate)

Write a query that connects books to genres across the book_genres junction table to show each book title alongside its associated genre names:

SELECT 
    books.title,
    genres.name AS genre
FROM books
INNER JOIN book_genres ON books.id = book_genres.book_id
INNER JOIN genres ON book_genres.genre_id = genres.id;

Extend this query to include the author’s name from the authors table as well.

Activity 2: Grouped String Aggregation (Intermediate)

Query each book along with a single comma-separated list of all genres assigned to it:

  • In SQLite: Use GROUP_CONCAT(genres.name, ', ').
  • In PostgreSQL: Use STRING_AGG(genres.name, ', ').
SELECT 
    books.title,
    GROUP_CONCAT(genres.name, ', ') AS all_genres
FROM books
INNER JOIN book_genres ON books.id = book_genres.book_id
INNER JOIN genres ON book_genres.genre_id = genres.id
GROUP BY books.id;
